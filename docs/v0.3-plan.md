# Meshnology Web Flasher v0.3 — Firmware Catalog (static)

> Architecture & decision record. v0.2 (local upload only) → v0.3
> (pre-built firmware catalog served as static assets, with device-
> aware URL routing and a dual-mode UI that supports both catalog and
> local upload).

## TL;DR

v0.2 lets you flash a `.bin` you drag in. v0.3 keeps that flow but
also serves **pre-built firmware** alongside the tool, so a user
opens `https://meshnology-flasher.pages.dev/?device=w20-meshnology&version=1.0.0`
and gets a guided "select device → select version → flash" flow that
no longer requires them to find a `.bin` on their own.

Firmware and catalog are **static files in the repo**, served by
Cloudflare Pages from `public/firmware/` and `public/catalog/`. The
owner publishes a new firmware by committing a `.bin` and a small
JSON metadata update — no R2, no Functions, no third-party storage,
no extra credentials.

**Monthly cost: $0** (Cloudflare Pages free tier, unlimited).

## What's new vs v0.2

| Capability | v0.2 | v0.3 |
|---|---|---|
| Flash a `.bin` you provide | ✅ | ✅ (mode A) |
| Pre-built firmware catalog | ❌ | ✅ (mode B) |
| Device-aware URL routing | ❌ | ✅ `?device=xxx&version=yyy` |
| Owner publishes by | hand the bin to the user | commit to repo |
| Backend required | none | none (still none) |
| Pages Functions | n/a | n/a (rejected in design) |
| R2 / object storage | n/a | n/a (rejected in design) |

## Two flash modes (UI)

### Mode A: bring your own .bin (default — no URL params)

```
┌─ Step 01 ─────────────────┐
│ Choose serial port       │
└──────────────────────────┘
┌─ Step 02 ─────────────────┐
│ Drag a .bin here          │   ← user picks file
│ or  [Browse catalog ▾]    │   ← jump to Mode B
└──────────────────────────┘
┌─ Step 03 ─────────────────┐
│ Start flashing            │
└──────────────────────────┘
```

### Mode B: pick a device + version (`?device=xxx[&version=yyy]`)

```
┌─ Step 01 ─────────────────┐
│ Choose serial port       │
└──────────────────────────┘
┌─ Step 02 ─────────────────┐
│ Device:  w20-meshnology   │   ← from URL or device picker
│ Version: [1.0.0 ▾]         │   ← version dropdown
│ or  [Drop custom .bin]    │   ← escape hatch back to Mode A
└──────────────────────────┘
┌─ Step 03 ─────────────────┐
│ Start flashing            │
│   w20-meshnology 1.0.0    │   ← chip metadata shown
│   1.25 MB · SHA-256 verified │
└──────────────────────────┘
```

The two modes share the same Step 01 and Step 03 code. Only Step 02
differs. A user can switch from A to B by clicking "Browse catalog"
in Step 02, or back from B to A by dropping a `.bin`.

## Catalog data format

### `public/catalog/manifest.json`

```json
{
  "schemaVersion": 1,
  "updated": "2026-10-16T09:00:00Z",
  "devices": [
    {
      "id": "w20-meshnology",
      "displayName": "W20 Meshnology (ESP32-S3)",
      "vendor": "Meshnology",
      "chip": "ESP32-S3",
      "latestVersion": "1.0.0",
      "flashSize": "16MB",
      "notes": "Factory firmware for W20 board with PSRAM 8MB"
    },
    {
      "id": "gat562",
      "displayName": "GAT-IoT GAT562 30S",
      "vendor": "GAT-IoT",
      "chip": "ESP32-S3",
      "latestVersion": "2.1.0",
      "flashSize": "8MB"
    }
  ]
}
```

### `public/catalog/devices/{id}.json`

```json
{
  "id": "w20-meshnology",
  "displayName": "W20 Meshnology (ESP32-S3)",
  "vendor": "Meshnology",
  "chip": "ESP32-S3",
  "flashSize": "16MB",
  "notes": "Factory firmware for W20 board",
  "versions": [
    {
      "version": "1.0.0",
      "size": 1310112,
      "sha256": "ab12cd34...",
      "uploaded": "2026-10-16T09:00:00Z",
      "filename": "w20-meshnology-1.0.0.bin",
      "notes": "Initial release"
    }
  ]
}
```

The `sha256` is the SHA-256 of the `.bin` file, computed once at
publish time. The frontend uses it for client-side integrity check
before passing the bytes to esptool.js (catches CDN corruption, MITM,
and stale caches).

### Naming and validation

- `device.id` matches `/^[a-z0-9][a-z0-9-]{0,40}$/` (lowercase + digits + dash)
- `version` matches `/^\d+\.\d+\.\d+([+-][A-Za-z0-9.-]+)?$/` (semver-ish)
- `sha256` is a 64-char lowercase hex string
- `size` is in bytes (matches `Content-Length` of the .bin)

Anything that fails these patterns returns `404 CATALOG_INVALID` from
the frontend and is not selectable.

## Frontend behavior

### Boot flow (modes A and B)

```
main.ts:
  1. parse URLSearchParams → { device, version } | null
  2. if (device) → setMode('catalog')
       fetch /catalog/manifest.json   → show device picker (if device param missing)
       fetch /catalog/devices/{id}.json → show version dropdown
  3. else → setMode('upload')           // v0.2 default
  4. on Start flashing click:
       upload mode  → read .file.arrayBuffer() → flashEsp32
       catalog mode → fetch /firmware/{id}/{version}.bin
                    → SubtleCrypto.digest('SHA-256', bytes)
                    → if digest != catalogEntry.sha256: throw FIRMWARE_CORRUPTED
                    → else flashEsp32
```

### URL routing

| URL | Mode | UI shows |
|---|---|---|
| `/` | A (upload) | drag .bin area |
| `/?device=w20-meshnology` | B (catalog) | version dropdown for that device |
| `/?device=w20-meshnology&version=1.0.0` | B (catalog, preselected) | "Ready · 1.25 MB" + Start enabled |
| `/?device=does-not-exist` | B (catalog, error) | "Device not found, pick another" |
| `/?device=w20&version=99.99.99` | B (catalog, error) | "Version not found, latest 5 shown" |

### SHA-256 verification

```ts
const expected = catalogEntry.sha256;
const actual = await crypto.subtle.digest('SHA-256', bytes);
const actualHex = Array.from(new Uint8Array(actual))
  .map(b => b.toString(16).padStart(2, '0')).join('');
if (actualHex !== expected) {
  throw new FlashError('FIRMWARE_CORRUPTED', `expected ${expected} got ${actualHex}`);
}
```

Replaces the v0.2 MD5 whole-image check that never worked (esptool.js
needs sync MD5; SubtleCrypto is async).

## Security

| Threat | Mitigation |
|---|---|
| Malicious firmware | SHA-256 client-side verify |
| Stale / cached bin | SHA-256 catches a tampered cache too |
| Path injection | device/version regex-validated; static file paths constructed only from validated strings |
| Cross-origin abuse | n/a — same-origin static assets |
| MITM | HTTPS (Cloudflare auto) |
| Firmware theft | `.bin` files are public by design (anyone can curl them). Acceptable for a flashing tool. Add per-device auth in v0.4 if needed. |

## Git LFS

`public/firmware/` is binary. Plain `git add` of N×5-16 MB .bin files
will bloat the repo over time. For v0.3 we accept this. For v0.3.1:

- Switch firmware `.bin` files to **Git LFS** storage
- Pages supports LFS files automatically (the build copies them to
  `dist/firmware/`); no extra Cloudflare config needed
- Repo stays small; LFS objects live on GitHub's LFS server (free tier
  1 GB storage, 1 GB bandwidth/month — enough for tens of devices)

If you have private LFS data, you can also use **r2 + presigned
URLs** for direct firmware download (out of v0.3 scope, but a v0.4
option).

## Why not R2 / Pages Functions?

The original v0.3 plan proposed Cloudflare R2 + three Pages Functions.
We changed our mind because:

| Concern | R2 + Functions path | Static path |
|---|---|---|
| Owner publishing | needs `wrangler` CLI + R2 write token | just `git commit` |
| Third-party storage | R2 bucket lifecycle, CORS, egress policy | n/a |
| CORS for SPA fetch | one extra CORS rule | same-origin, no CORS |
| Serverless cold start | ~50 ms first call | n/a (static) |
| Catalog consistency | catalog JSON can drift from bin reality (need a deploy script) | commit errored if sha256 doesn't match |
| Vendor lock-in | Cloudflare-specific | plain HTTP, deploys anywhere |

The trade-off is **repo size** (firmware lives in git), which is
manageable for a few devices and gets fixed with LFS later.

## What's NOT in v0.3

- ❌ Admin UI for publishing (use git)
- ❌ User login / role-based access
- ❌ OTA over the air
- ❌ Firmware signing / GPG-style trust chain (SHA-256 only, not signature)
- ❌ Auto-detect "which firmware does my board need"
- ❌ Multi-segment flashing (multi mode UI exists but writes single segment at offset 0)
- ❌ iOS Safari (Web Serial is desktop-only)
- ❌ Custom stub / 80 MHz SPI (still ROM default 40 MHz)
- ❌ Database (catalog is files, bin is files)
- ❌ Cloud-side analytics
