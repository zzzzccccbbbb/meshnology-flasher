# Meshnology Web Flasher v0.3 — Cloud Firmware Catalog

> Architecture & decision record. v0.2 (local upload only) → v0.3
> (cloud-hosted firmware catalog with device-aware URL routing).
> Implementation blocked until this is approved.

## TL;DR

The v0.2 tool works for **owner-local flashing** (you on your dev machine
with your dev server). To turn it into a public tool where users open
**`meshnology-flasher.pages.dev/?device=gat562&version=2.1.0`** and
flash with zero local setup, v0.3 adds:

- A **Cloudflare Pages** static site (free, automatic HTTPS, bound to
  GitHub `main` branch)
- A **Cloudflare R2** bucket storing firmware `.bin` files + a small
  JSON catalog
- Three **Cloudflare Pages Functions** (serverless) endpoints
  reading the catalog
- A frontend rewrite of the file-picker step to instead **fetch the
  selected firmware from R2** at the moment the user clicks
  **Start flashing**

**Monthly cost: $0** within Cloudflare's free tier (10 GB R2, unlimited
Pages bandwidth, 100k Pages-Functions requests/day).

## Why this stack

Considered:

| Stack | Verdict |
|---|---|
| **Cloudflare Pages + R2 + Pages Functions** | ✅ chosen — single provider, generous free tier, R2 egress is always free |
| Vercel + Vercel KV / Blob | works but Blob free tier is 500 MB; R2 gives 10 GB |
| AWS S3 + CloudFront | works but egress costs blow up; ops overhead |
| Self-hosted VPS ($5/mo) | extra ops, single point of failure |
| GitHub Pages | can't host backend, dropped |

Cloudflare R2's distinguishing feature is **zero egress fees** — the
10 GB / 1 GB-class free tier beats S3 (which charges ~$0.09/GB egress)
for the same use case.

## Data flow

### Cold path: owner publishes a new firmware

```bash
# 1. compile firmware locally
cd ~/work/gat562-fw && idf.py build

# 2. compute SHA-256 of the .bin
sha256sum build/gat562_v2.1.0.bin

# 3. upload the bin to R2
npx wrangler r2 object put firmware-bin/gat562/2.1.0.bin \
   --file build/gat562_v2.1.0.bin

# 4. update the device catalog JSON
npx wrangler r2 object put firmware-catalog/devices/gat562.json \
   --file ./gat562.json
# where ./gat562.json is:
# {
#   "device": "gat562",
#   "displayName": "GAT-IoT GAT562 30S",
#   "versions": [
#     {
#       "version": "2.1.0",
#       "size": 1234567,
#       "sha256": "ab12cd34...",
#       "uploaded": "2026-09-18T10:00:00Z",
#       "notes": "Stable release"
#     }
#   ]
# }

# 5. update the top-level manifest
npx wrangler r2 object put firmware-catalog/manifest.json --file ./manifest.json
# where ./manifest.json is:
# {
#   "devices": [
#     { "id": "gat562", "displayName": "GAT-IoT GAT562 30S", "latest": "2.1.0" },
#     { "id": "w20",    "displayName": "W20 Meshnology",     "latest": "1.0.0" }
#   ]
# }
```

### Hot path: user opens a link and flashes

```
1. Browser loads https://flasher.meshnology.com/?device=gat562&version=2.1.0
2. main.ts reads URL search params
   → device = "gat562", version = "2.1.0"
3. Fetch /api/firmwares?device=gat562
   → user sees the version list with v2.1.0 highlighted
4. User clicks "Start flashing"
5. Fetch /api/firmware/gat562/2.1.0
   → returns bytes (verified by SHA-256 in browser)
6. Hand bytes to esptool.js
7. Flash
8. Done.
```

## API surface

All three endpoints are Cloudflare Pages Functions (serverless). They
read from the R2 bucket and return JSON or bytes.

### `GET /api/devices`

```json
{
  "ok": true,
  "devices": [
    { "id": "gat562", "displayName": "GAT-IoT GAT562 30S", "latest": "2.1.0" },
    { "id": "w20",    "displayName": "W20 Meshnology",     "latest": "1.0.0" }
  ]
}
```

### `GET /api/firmwares?device=gat562`

```json
{
  "ok": true,
  "device": "gat562",
  "versions": [
    {
      "version": "2.1.0",
      "size": 1234567,
      "sha256": "ab12cd34...",
      "uploaded": "2026-09-18T10:00:00Z",
      "notes": "Stable release"
    },
    { "version": "2.0.0", "size": 1230000, "sha256": "..." }
  ]
}
```

### `GET /api/firmware/:device/:version`

```
200 OK
Content-Type: application/octet-stream
Content-Length: 1234567
X-Firmware-Sha256: ab12cd34...

[binary bytes of the .bin]
```

### 4xx errors

All endpoints return `{ok: false, error: "<code>", message: "..."}`:

- `400 DEVICE_INVALID` — `device` not matching `[a-z0-9-]+`
- `400 VERSION_INVALID` — `version` not matching `[a-z0-9.-]+`
- `404 DEVICE_NOT_FOUND` — no catalog entry for the device
- `404 VERSION_NOT_FOUND` — no version matches for the device
- `404 FIRMWARE_MISSING` — catalog has the entry but the bin is not in R2
- `500 R2_ERROR` — R2 read failure
- `504 R2_TIMEOUT` — R2 read exceeded 30 s

## R2 bucket structure

```
firmware-catalog/                      metadata only (small JSON, fast reads)
  manifest.json
  devices/
    gat562.json
    w20-meshnology.json
    mt-762.json

firmware-bin/                          actual .bin (could be 5–16 MB each)
  gat562/
    2.1.0.bin
    2.0.0.bin
  w20-meshnology/
    1.0.0.bin
```

The split (`firmware-catalog` vs `firmware-bin`) lets us have a much
stricter CORS / cache policy on the catalog (short-TTL) versus the bin
files (long-TTL with `immutable`).

## Frontend changes

### URL routing

`main.ts` reads `URLSearchParams`:

| URL | Behavior |
|---|---|
| `/` | Show device picker (Step 02 becomes the device picker) |
| `/?device=gat562` | Show version picker for gat562 |
| `/?device=gat562&version=2.1.0` | Auto-select, "Start flashing" enabled immediately |

### New files

```
src/
  catalog/
    api.ts              fetch wrapper for /api/devices, /api/firmwares
    reader.ts           fetch /api/firmware/:device/:version -> Uint8Array + SHA-256 verify
    types.ts            Device, FirmwareVersion types
    api.test.ts         unit tests (mock fetch)
  main.ts               modified: URL param parsing, fetch on load
  i18n.ts               new keys: catalogLoading, catalogError, versionLabel, etc.
```

### Modified flow

v0.2: user drags .bin → File object → flashEsp32(port, [file], ...)

v0.3: main.ts fetches selected firmware → Uint8Array → flashEsp32(port, [{bytes, name, offset}], ...)

The `flashEsp32` API already accepts `Uint8Array` (`FlashFile.bytes`),
so the **flasher layer doesn't change** at all. We only change the
**input source** (File → fetch).

### SHA-256 verification

Before passing bytes to esptool.js:

```ts
const expected = catalogEntry.sha256;
const actual = await crypto.subtle.digest('SHA-256', bytes);
const actualHex = Array.from(new Uint8Array(actual))
  .map(b => b.toString(16).padStart(2, '0')).join('');
if (actualHex !== expected) throw new FlashError('FIRMWARE_CORRUPTED', ...);
```

The v0.2 MD5 whole-image check is a separate, deeper issue (esptool.js
sync vs SubtleCrypto async — see `flasher.ts` Stage 2.x history).
For v0.3 we adopt **SHA-256 client-side verify** instead, which solves
two problems at once: (1) we know the bytes match what R2 served, and
(2) we replace the broken MD5 path.

## Security

| Threat | Mitigation |
|---|---|
| R2 bucket publicly readable | Bucket is **public-read** by design (firmware is meant to be downloadable), but no write access — only Cloudflare Access tokens (which only you have) can write |
| Cross-origin abuse | R2 has CORS rules allowing **only** `flasher.meshnology.com` and `meshnology-flasher.pages.dev` for GETs; all writes blocked at bucket level |
| Path injection | `device` and `version` regex-validated: `/^[a-z0-9._-]+$/i` |
| Man-in-the-middle | HTTPS (Cloudflare auto) |
| Stale / malicious firmware | SHA-256 client-side verify |
| Rate-limit abuse | Cloudflare's default WAF + rate limit (free tier) |

## Cost analysis

| Service | Free tier | Realistic usage | Cost |
|---|---|---|---|
| Cloudflare Pages | Unlimited requests, unlimited bandwidth | 1k visits/day, 1MB download per flash | **$0** |
| Cloudflare R2 storage | 10 GB / month | 5 devices × 5 versions × 8 MB = 200 MB | **$0** |
| Cloudflare R2 class A operations (writes) | 1M / month | You publish 1 firmware/week = 4/mo | **$0** |
| Cloudflare R2 class B operations (reads) | 10M / month | 1k users × 1 firmware each = 1k reads | **$0** |
| Cloudflare R2 egress | **Always free** | 8 GB / month egress | **$0** |
| Cloudflare Pages Functions requests | 100k / day | 1k / day | **$0** |
| **Total** | | | **$0 / month** |

If you exceed 10 GB R2 storage (very unlikely) the overage is
$0.015/GB-month. If you exceed 100k Pages Functions requests / day
(unlikely for a niche tool) the overage is $0.30 per million.

## What's NOT in v0.3 (explicit non-goals)

- ❌ Admin UI (you use `wrangler` CLI to publish)
- ❌ User login / role-based access
- ❌ OTA over the air
- ❌ Firmware signing / GPG-style trust chain
- ❌ Auto-detect "which firmware does my board need"
- ❌ Multi-segment flashing (offsets > 0)
- ❌ iOS Safari
- ❌ Custom stub / 80 MHz SPI (still ROM default 40 MHz)
- ❌ Dynamic device config (hard-coded in catalog JSON)
- ❌ Database (R2 is the only "DB")

## Risk matrix

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Cloudflare pricing changes | low | mid | the $0 tier has been stable since 2022; we'd have years of warning |
| R2 free tier exceeded | low | low | $0.015/GB-month is cheap; alert at 5 GB |
| Pages Functions request limit exceeded at launch | low | low | $0.30/million overage |
| Mis-uploaded firmware corrupts boards | low | high | SHA-256 client-side verify catches it before flash |
| Catalog JSON inconsistency (catalog says bin exists, but R2 doesn't have it) | low | mid | API returns `404 FIRMWARE_MISSING`, UI prompts re-download |
| User cannot use Web Serial (Safari) | medium | low | UI shows clear "unsupported browser" notice |
