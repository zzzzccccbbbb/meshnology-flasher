## 1. 决策摘要

| 维度 | 选型 |
|---|---|
| 烧录引擎 | `esptool-js` (Espressif 官方，MIT) |
| 浏览器 API | **Web Serial**（`navigator.serial`） |
| 固件来源 | **仅本地 .bin**（云端要后端，v0.3 再做） |
| 会员 / 登录 | ❌ 不做 |
| 支持芯片 | 全谱（ESP32 / S2 / S3 / C2 / C3 / C5 / C6 / C61 / H2 / P4 / ESP8266） |
| UI 流程 | 三步：连接 → 匹配芯片 → 烧录（参考 16302/xiaozhiinit） |
| 终端显示 | XTerm.js，实时显示 esptool stdout |
| Flash 配置 | 三档（mode / freq / size），智能默认 |

|---|---|---|

| `CbVKve0s.js` | Web Serial transport 适配层（write pacing、SLIP 封装） | 1.2KB |
| 其他 8 个子 chunk | 各芯片型号的 loader | 共 ~33KB |

**关键证据**：
- `CYuQ-84T.js:1` `class T { esploader; chipinfo; FLASH_BAUDRATE=460800; ... this.transport; this.terminal; ... start_erase_flash; start_program(file, flashConfig) { ... esploader.write_flash({fileArray, flashSize, flashMode, flashFreq, eraseAll:false, compress:true, reportProgress}) ... } }`
  ← **这就是 esptool.js 的 ESPLoader + write_flash API，直接套壳**
- `CnuYZAQG.js:2` 复位序列 `class ot { reset() { setDTR(false); setRTS(true); delay(100); ... } }` ← **典型 ESP32 ROM bootloader 复位序列**
- `CnuYZAQG.js:2` `switch(l) { case "ESP32": import("./DIlGCCSz.js"); case "ESP32-S3": import(...); ... }` ← **按芯片型号动态 import**
- `CbVKve0s.js:1` `slipWriter; trace; hexConvert; device.writable.getWriter()` ← **Web Serial WritableStream + SLIP 编码**

**没有 .wasm**，**没有外部 stub binary**，esptool.js 完全用 JS 实现，可以直接 bundle 进 vite。

## 4. 技术选型理由

### 4.1 为什么 Web Serial 而不是 WebUSB

| | Web Serial | WebUSB |
|---|---|---|
| ESP32-S3 DevKit (CH340/CP210x) | ✅ 直接用 | ❌ USB-TTL 转接芯片是 USB CDC-ACM 设备类，需要 manufacturer-specific control transfer，复杂 |
| ESP32-S3 内部 USB OTG | ✅ 通过 CDC-ACM | ✅ 但要自己写 transport 桥 |
| 浏览器支持 | Chrome 89+ / Edge 89+ | Chrome 61+ / Edge 79+（但 ESP32 用例不直观） |
| esptool-js 官方支持 | ✅ 默认走 Web Serial | ⚠️ 有 WebUSB transport 但维护少 |
| 设备选择 UX | 串口名（COM3, /dev/ttyUSB0） | 厂商名+产品名（不直观） |
| 16302/xiaozhiinit 用法 | ✅ 一致 | ❌ |

**结论**：Web Serial + esptool-js 是社区主流路线，无任何理由改 WebUSB。

### 4.2 为什么 esptool-js 而不是自研协议栈

| | esptool-js | 自研 SLIP |
|---|---|---|
| 工作量 | 集成 1 天 + UI 1 天 | 写协议栈 8 周 + UI 1 周 |
| 协议覆盖 | 11 款芯片 + stub 自动加载 + MD5 校验 + flash 加密开关 | v0.2 只能 1 款芯片 |
| 维护 | 上游 Espressif 维护 | 自己修（bootloader 时序坑多） |
| 风险 | **低**（社区跑了 5+ 年） | **高** |
| 用户感知差异 | 0 | 0 |

**结论**：自研协议栈没有任何用户可感知的好处，只增加工时和风险。

### 4.3 为什么纯本地 .bin，不要云端

- 云端固件 = 后端 API + 数据库 + 文件存储 + 版本管理 + 签名校验，**至少 1 周后端活**
- 你现在 v0.2 目标是"能烧"，云端是 v0.3 的事
- 用户能自己提供 .bin 就不需要云端

### 5.2 数据流

```
[file input] → File
            ↓
       validateSegments()   (已有)
            ↓
       选 flashConfig（mode/freq/size）→ 默认值或用户改
            ↓
[Web Serial 选择端口] → port (SerialPort)
            ↓
[flash click] → flashEsp32(port, file, flashConfig, cb)
            ↓
       transport = new WebSerialTransport(port)         // esp32/transport.ts
       esploader = new ESPLoader(transport, baudrate)   // esptool-js
            ↓
       await esploader.initialize()                     // 复位 + SYNC + chip detect
       esploader.chip → chipDetect.friendlyName()       // "ESP32-S3" 等
            ↓
       await esploader.writeFlash({
         fileArray: [{data, address:0}],
         flashSize, flashMode, flashFreq,
         eraseAll: false,
         compress: true,
         reportProgress: (fileIdx, written, total) => onProgress({...})
       })
            ↓
       esploader.after()  // 软复位
       transport.disconnect()
            ↓
       cb.onProgress({phase:'done', written:total, total}) / cb.onLog('OK')
```

## 8. 错误处理矩阵（11 条）

| 错误 ID | 触发条件 | 用户看到（中/英） | 内部动作 |
|---|---|---|---|
| `BROWSER_UNSUPPORTED` | 无 `navigator.serial` | "不支持 / Use Chrome 89+ or Edge 89+" | disable #flash |
| `NO_PORT` | 用户没选端口就烧 | "请先连接串口 / Connect a serial port first" | UI 已有 |
| `SERIAL_OPEN_FAIL` | `port.open()` 抛异常 | "无法打开串口 / Cannot open port (其他程序占用？)" | UI 提示 |
| `SYNC_TIMEOUT` | esptool 同步失败 | "ROM 同步失败：按住 BOOT 再插 / Sync failed: hold BOOT and replug" | disconnect + 提示 |
| `CHIP_UNKNOWN` | esptool 不认识芯片 | "无法识别芯片 / Unknown chip" | disconnect |
| `BIN_TOO_LARGE` | .bin > flash size | "固件超出 Flash 大小 / Firmware exceeds flash size" | 提前 return |
| `ERASE_FAIL` | erase 阶段报错 | "擦除失败 / Flash erase failed" | disconnect |
| `WRITE_FAIL` | 写阶段报错 | "写入失败 @ 0x{addr} / Flash write failed @ 0x{addr}" | disconnect |
| `VERIFY_FAIL` | MD5 不匹配 | "校验失败 / MD5 mismatch" | disconnect |
| `PORT_DISCONNECT` | 烧录中拔线 | "串口已断开 / Serial port disconnected" | disconnect + UI 重置 |
| `ABORTED` | 用户点取消 | "已取消 / Cancelled" | disconnect |

每条都要在 esptool.js 抛出的错误类型 / 字符串里匹配关键字映射（不能改 esptool 内部）。

## 9. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| `esptool-js` npm 包最新版与 esptool.py 不一致 | 行为差异 | 锁版本（用 git tag 或具体版本号），v0.3 升级前重测 |
| Web Serial 在某些 Linux 上需要 udev 规则 | 用户跑不起来 | README 写 udev 规则命令 |
| ESP32-S3 内部 USB OTG 用户 | esptool-js 也能跑，但要走 USB-OTG transport | v0.3 加 transport 选择；v0.2 README 注明"v0.2 推荐外置 USB-TTL" |
| esptool-js 的 stub loader 在某些 ROM 版本失败 | 写入失败 | README 注明仅验证 ESP32-S3；其它芯片由用户实测 |
| XTerm 在低端机性能 | UI 卡 | `disableStdin: true`，不接收用户输入只显示输出 |
| Web Serial 在非 https 下不能用 | 本地 dev OK，部署后用户访问失败 | README 强调需 https（GitHub Pages / Vercel / Cloudflare 都 OK） |

## 15. 决策记录：为何放弃 v1（自研 SLIP 路线）

**v1 假设**：可以自己写 SLIP 协议栈 + WebUSB，能完全脱离 esptool。

**推翻证据**：
1. 抓回 16302/xiaozhiinit 的全部 100KB esptool.js 拆包后发现，**所有产品级 web flasher 都用 esptool-js**，没有自研案例
2. 自研路线需要翻译 esptool.py 的 ~8000 行 Python 到 TS，工时 8 周+
3. 自研只能覆盖 1 款芯片（v0.2），产品级必须 11 款
4. 用户可感知价值为 0（都能烧），只是工程取舍
