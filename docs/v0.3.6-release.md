# v0.3.6 — layout refactor + UI fixes

ESP32 flashing was already working end-to-end on real hardware (see
"Verified on hardware" below). This release is entirely about how the
page presents that: the three-card step grid is gone, replaced by the
two-column file box from 16302.com/localinit, and the firmware source
is picked with real tabs instead of a ghost button.

Everything functional was kept: local upload, device catalog with
SHA-256 verification, single vs. multiple files with per-file offsets,
flash parameters, live progress and the esptool.js terminal.

## Layout

    +---------------------+----------------------------------------+
    | Connect device      | Select firmware                        |
    |  - status badge     |  [ Local upload ] [ Pick a device ]    |
    |  - connect button   |  [ Single .bin ] [ Multi + offsets ]    |
    |  - serial info      |  drop zone / device + version picker   |
    |  CHIP: ...          |  flash parameters (mode/freq/size)     |
    +---------------------+----------------------------------------+
    CHIP: ...
    [ Flash single file ]                  <- label follows selection
    progress bar
    esptool.js terminal

* `page-head` — one title and one sentence, no marketing block
* `file-box` — a single 4px amber frame, left column ~32% (device and
  serial), right column ~68% (firmware), collapsing to one column
  below 720px
* `burn-row` — chip readout, the burn button, progress, terminal

## Behaviour

* **Two source tabs.** `Local upload` and `Pick a device` are peers now.
  The single/multi tabs live inside the upload pane.
* **One burn button whose label follows the selection:**
  * upload + single → "Flash single file" / 单文件烧录
  * upload + multi → "Flash multi file" / 多文件烧录
  * catalog → "Flash device firmware" / 烧录设备固件

  There is one pipeline either way: `esptool-js`'s `writeFlash` takes
  `fileArray: [{data, address}]`, and a single-file upload is that array
  with one entry. Before this release the multi button silently forced
  `uploadMode` to `multi`, contradicting the tab the user had just
  picked.

* **The multi button's 2-file gate is gone.** It only existed to
  distinguish two buttons; one file in multi mode is a valid write
  (one image at one offset).

* **Flash parameters default to DIO / 80 MHz / 16 MB**, not Auto. Auto
  fails on the test board: the chip is detected fine but the SPI flash
  parameter read returns nothing and the write aborts immediately.
  Other boards can still pick Auto manually.

* **Language switching is page-wide.** Previously only the file list
  re-rendered, so step titles, button labels and parameter labels stayed
  in the old language. Static strings carry `data-i18n="<key>"` and
  `applyLanguage` walks them.

## Verified on hardware

ESP32-S3 DevKitC, native USB (VID `0x303A` / PID `0x1001`), MAC
`44:bd:8d:eb:ea:68`, flash id `1840ef`:

```
Detecting chip type... ESP32-S3 (QFN56) (revision v0.2)
Crystal is 40MHz   Features: Wi-Fi, BLE, Embedded PSRAM 8MB (AP_3v3)
Flash ID: 1840ef   [esptool] Flash params set to 24f
Compressed 1298224 bytes to 766931...
Wrote 1298224 bytes (766931 compressed) at 0x0 in 11.2 seconds.
Hard resetting via RTS pin...
```

Two boards flashed twice each with no error.

## Not verified on hardware

* **Multi-file write.** The offset assignment (`0x0` / `0x8000` /
  `0x10000` following `idf.py build`'s `flash_args`) and the esptool.js
  call path are in place and unit-reachable, but three files have not
  been written to a real board in one session.
* **Catalog flash under the new layout.** Catalog mode worked before
  the refactor (`?device=w10-meshnology&version=1.0.0`); the reworked
  pane has not been re-run against a board.
